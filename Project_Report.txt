Abstract
========

This project is about making an online multiplayer game where people guess words by looking at drawings. The main goal is to create a fun and easy-to-use game that works smoothly, even when many people are playing at the same time. Many similar games have problems like slow response, hard-to-find matches, and cheating. To solve these, we built a backend server using NestJS for fast and stable performance, and a frontend with ReactJS for a friendly user interface. The game uses WebSocket for real-time drawing and guessing, and players can join rooms with up to eight people. We also added security features like login with JWT and checks to stop cheating. All game data, like scores and rooms, is saved in a PostgreSQL database. The whole system is put into Docker containers and deployed on the cloud, so it can handle more users easily. We tested the game and improved it based on feedback. In the end, this project shows how to make a simple, secure, and enjoyable online drawing game that gives players a better experience than many existing games.

Introduction
============

Background and Problem
----------------------
Online drawing and guessing games have become popular because they are fun and help people connect with friends or strangers. However, many of these games have problems like slow response times, hard-to-find matches, and cheating. These issues make the games less enjoyable and sometimes unfair. The main reason for these problems is poor server performance, bad matchmaking systems, and weak security.

Rationale and Scope
-------------------
This project aims to solve these problems by building a better backend system for a scribble game. The goal is to make the game fast, fair, and easy to use. The project covers both the backend (using NestJS) and the frontend (using ReactJS), with a focus on real-time communication, security, and a good user experience. The scope includes creating game rooms, real-time drawing and guessing, a scoring system, and security features to prevent cheating.

Aims and Objectives
-------------------
The main aim is to create an online multiplayer scribble game that is smooth, secure, and fun. The objectives are:
- Build a backend server with NestJS for low-latency and stable performance.
- Create a frontend with ReactJS for a friendly and responsive user interface.
- Use WebSocket for real-time drawing and guessing.
- Allow up to eight players in a room, with easy room creation and joining.
- Add a fair scoring system based on how fast players guess the word.
- Use JWT authentication and other checks to stop cheating.
- Deploy the system on the cloud using Docker for easy scaling.

These objectives are SMART: Specific, Measurable, Achievable, Relevant, and Time-bound.

Method and Architecture
-----------------------
The system uses a client-server model. The frontend (ReactJS) handles user actions and shows the game. The backend (NestJS) manages the game logic, rooms, and scores, and uses WebSocket for real-time updates. PostgreSQL is used to store user data, scores, and room info. Everything is put into Docker containers and deployed on a cloud platform, so the game can support many users at once. This setup is chosen because it is modern, scalable, and reliable.

Overview of the Solution
------------------------
Players can create or join game rooms using a code. Each round, one player draws a word, and others try to guess it. Points are given based on how quickly players guess the word. The game continues for several rounds, and the player with the most points wins. Security features make sure the game is fair and safe.

Overview of the Report

The next chapters will explain the analysis of requirements, the design of the system, how the game was implemented, how it was tested, and the results. The report will also discuss what was learned, possible future improvements, and provide references and appendices with extra information.

Analysis
========

Requirements Specification
-------------------------

Functional Requirements (MoSCoW Prioritization)
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
Functional requirements describe what the system must do to meet the needs of its users. In this project, the most important features are related to user authentication, room management, and real-time gameplay. Users must be able to register and log in securely using JWT authentication, which ensures that only authorized players can access the game. This is crucial for protecting user data and preventing unauthorized access. For example, if a user tries to join a game without a valid token, the system will reject the connection and prompt the user to log in again. This helps prevent cheating and keeps the game fair for everyone.

Creating and joining rooms is a core part of the experience, and rooms can be protected with passwords for privacy. This allows friends to play together in private games, while public rooms are open to anyone. Each room can have up to 8 players, and settings like the number of rounds and maximum players can be adjusted by the host. This flexibility lets users customize their gaming experience. For example, a group of friends might want a quick game with only 4 rounds, while another group might prefer a longer session with the maximum number of rounds. The system checks for edge cases, such as trying to join a full room or entering the wrong password for a private room, and provides clear error messages to guide the user.

During the game, a drawer is chosen each round and is given three random words to pick from. The drawer then draws the chosen word, while other players try to guess it in real time using the chat system. This real-time interaction is made possible by WebSocket connections, which allow for instant updates and smooth gameplay. The system tracks scores and displays them after each round, so players can see how they are doing compared to others. The game ends after all rounds are completed, and the winner is announced based on the total score. This competitive element encourages players to do their best and adds excitement to the game.

To keep the game fair, cheating is prevented by securing WebSocket connections and requiring JWT for all real-time communication. For example, if a player tries to send fake drawing data or guess messages without proper authentication, the system will block these actions. If the room owner leaves, the system automatically assigns a new owner, so the game can continue smoothly without interruption. This is important for maintaining the flow of the game and ensuring that players are not left stranded if the host disconnects. Real-time notifications keep all players updated about important room events, such as users joining or leaving and room creation. These notifications help players stay informed and engaged throughout the game.

Some features are not absolutely essential but improve the user experience. For example, players can chat during the game, see a timer for each round, and view a list of participants in the room. The chat feature allows for friendly banter and teamwork, while the timer adds a sense of urgency and keeps the game moving at a good pace. The participant list helps players know who is in the room and who is currently drawing. The system also allows players to leave and rejoin rooms, which is useful if someone loses their connection or needs to step away for a moment. Private rooms can be protected with passwords, giving users control over who can join their games. Features like custom avatars, custom word lists, and sound effects are considered nice-to-have but are not the main focus at this stage. These features could be added in the future to further enhance the game. The project will not support more than 8 players per room or AI bots for now, as these are outside the current scope and would require significant additional development.

User Stories and Edge Cases
---------------------------
To better understand the functional requirements, it is helpful to consider some user stories and edge cases. For example, as a user, I want to be able to create a private room and invite my friends, so we can play together without strangers joining. As a player, I want to receive instant feedback when I guess the correct word, so I know I am doing well. As a host, I want to be able to start the game only when enough players have joined, so the game is fair for everyone. Edge cases include situations like two players trying to join the same room at the exact same time, or a player disconnecting in the middle of a round. The system must handle these cases gracefully, ensuring that the game continues smoothly and that all players are kept informed of any changes.

Error handling is also an important part of the functional requirements. For example, if a player tries to join a room that does not exist, the system should display a clear error message and suggest possible next steps. If a player enters the wrong password for a private room, the system should prompt them to try again or choose a different room. These details help create a user-friendly experience and reduce frustration for players.

Non-Functional Requirements
~~~~~~~~~~~~~~~~~~~~~~~~~~~
Non-functional requirements define how the system should perform and the quality standards it must meet. For this project, low latency is very important, so the system is designed to respond to user actions within one second. This is achieved by using efficient WebSocket communication and optimizing server performance. For example, when a player draws a line on the canvas, all other players should see the update almost instantly. If there is any noticeable delay, it can ruin the gaming experience and make the game less enjoyable.

The backend must be robust enough to handle at least 100 rooms running at the same time without crashing. This requires careful management of server resources and efficient handling of concurrent connections. The system uses Docker containers to isolate different parts of the application and make scaling easier. If the number of users increases, more containers can be added to handle the load. This scalability is important for supporting a growing user base and ensuring that the game remains available even during peak times.

Security is also a top priority, so all user data and game state are stored securely in the database, and all communication is encrypted using HTTPS and secure WebSocket connections. JWT authentication is used to verify the identity of each player and prevent unauthorized access. For example, if someone tries to intercept WebSocket messages or send fake data, the system will detect and block these attempts. Regular security audits and code reviews help identify and fix potential vulnerabilities before they can be exploited.

The system should be available 99% of the time, ensuring that players can access the game whenever they want. This is achieved by deploying the backend on reliable cloud platforms and using automated monitoring tools to detect and resolve issues quickly. If a server goes down, another one can take its place with minimal disruption to users. Backups are taken regularly to prevent data loss in case of hardware failure or other emergencies.

Usability is another important non-functional requirement. The user interface should be easy to use and accessible to players of all ages and skill levels. Clear instructions, intuitive controls, and helpful feedback messages make the game more enjoyable and reduce the learning curve for new users. The system is tested on different devices and browsers to ensure compatibility and a consistent experience for everyone.

Performance and Scalability
---------------------------
Performance is critical for a real-time multiplayer game. The system is designed to handle a large number of simultaneous users without slowing down or crashing. This is achieved through efficient use of server resources, load balancing, and horizontal scaling with Docker containers. The backend is optimized to minimize response times and ensure that all players receive updates as quickly as possible. For example, when a new player joins a room, all other players are notified immediately, and the game state is updated in real time.

Scalability is achieved by deploying the backend on cloud platforms that support automatic scaling. As the number of users grows, the system can add more containers or servers to handle the increased load. This ensures that the game remains responsive and available even during periods of high demand. Monitoring tools are used to track performance metrics and identify potential bottlenecks before they become problems.

Security and Data Protection
---------------------------
Security is built into every part of the system. JWT authentication is used to verify the identity of each player and protect against unauthorized access. All sensitive data, such as passwords and game state, is encrypted both in transit and at rest. The system uses secure coding practices and regular security audits to identify and fix vulnerabilities. For example, input validation is used to prevent SQL injection and other common attacks. Access controls are implemented to ensure that only authorized users can perform certain actions, such as creating or deleting rooms.

Data protection is also a key concern. The system takes regular backups of the database to prevent data loss in case of hardware failure or other emergencies. User data is stored in compliance with relevant privacy regulations, and users have control over their personal information. The system provides clear privacy policies and terms of service to inform users about how their data is used and protected.

Use Case Model
~~~~~~~~~~~~~~
The use case model describes the main actions that users can perform in the system and how the system responds. In this game, a typical flow starts with a user creating a new room, which can be public or private (with a password). The creator becomes the host and can adjust room settings. Other users join the room using a code and, if needed, a password. Players can leave the room at any time, and if the owner leaves, the system automatically assigns a new owner to keep the game running. When enough players have joined, the host starts the game. Each round, a player is chosen as the drawer and picks a word to draw from three options. The other players try to guess the word in real time using the chat. Points are awarded for correct guesses, and the drawer also gets points if someone guesses correctly. After all rounds, the game ends and the winner is announced. Throughout the game, players can chat and receive real-time notifications about important events, such as users joining or leaving the room.

For example, imagine a group of friends wants to play a private game. One user creates a room and sets a password. The others join using the room code and password. As the game progresses, each player takes a turn drawing, while the others guess. This architecture allows the system to handle many users and rooms at the same time, while keeping the experience fast and reliable. Security is enforced at every level, with JWT authentication required for all API and WebSocket connections.

The choice of NestJS for the backend provides a modular and maintainable codebase, making it easier to add new features and fix bugs. Docker containers allow for easy deployment and scaling, while cloud platforms provide the infrastructure needed to support a large user base. Monitoring and logging tools are used to track system performance and detect issues before they affect users.

TypeScript's static typing system significantly improved code quality by catching type errors at compile time, reducing runtime bugs and making the codebase more predictable. Testing

Introduction
------------
This chapter describes the approach taken to test the online multiplayer drawing and guessing game, ensuring that the system meets its functional and non-functional requirements. The testing strategy combined automated and manual techniques, including unit testing, integration testing, system testing, and user acceptance testing. The goal was to identify and resolve defects early, verify that all components worked together as intended, and ensure a robust, user-friendly experience. Testing Strategy
----------------
The project adopted a layered testing strategy:
- **Unit Testing:** Focused on individual functions and modules, ensuring that each part of the codebase worked as expected in isolation.
- **Integration Testing:** Verified that different modules interacted correctly, especially at the boundaries between backend services, database, and real-time communication layers.
- **System Testing:** Assessed the complete application in a production-like environment, simulating real user scenarios and edge cases.
- **Manual/User Testing:** Involved real users playing the game to uncover usability issues and unexpected behaviors that automated tests might miss.

Automated testing was prioritized for its repeatability and efficiency, while manual testing provided valuable feedback on user experience and system robustness.

Unit Testing
------------
Unit tests were written using the Jest testing framework, chosen for its speed, ease of use, and strong integration with TypeScript and NestJS. Each unit test targeted a specific function or class method, using mock data and dependencies to isolate the logic under test. The test scripts followed a clear structure: setup, execution, assertion, and teardown.

First Unit Test: Example and Explanation
----------------------------------------
The first unit test was developed for the user registration function in the backend authentication service. The purpose was to verify that a new user could be registered successfully and that the system handled duplicate registrations appropriately.

**Test Script (Simplified Example):**
```typescript
// user.service.spec.ts
import { UserService } from './user.service';
import { Test, TestingModule } from '@nestjs/testing';

describe('UserService', () => {
  let service: UserService;

  beforeEach(async () => {
    const module: TestingModule = await Test.createTestingModule({
      providers: [UserService],
    }).compile();
    service = module.get<UserService>(UserService);
  });

  it('should register a new user', async () => {
    const result = await service.register({
      email: 'test@example.com',
      username: 'testuser',
      password: 'securepassword',
    });
    expect(result).toHaveProperty('id');
    expect(result.email).toBe('test@example.com');
  });
});
```
**Explanation of Each Field:**
- `describe`: Defines the test suite for the UserService.
- `beforeEach`: Sets up a fresh instance of the service before each test, ensuring isolation.
- `it`: Defines an individual test case (registering a new user).
- `service.register`: Calls the registration method with mock data.
- `expect`: Asserts that the result contains the expected properties (e.g., a user ID and correct email).

**Test Execution:**
The test was run using the command `npm test`. The output showed a passing test, confirming that the registration logic worked as intended. (A screenshot of the test output is included in the appendix.)

Integration and System Testing
-----------------------------
Integration tests were designed to verify the interaction between modules, such as the authentication service, database, and WebSocket gateway. These tests used in-memory databases and mocked WebSocket connections to simulate real-world scenarios without affecting production data. For example, integration tests checked that a user could register, log in, join a room, and participate in a game round, with all state changes correctly reflected in the database.

User testing revealed areas for improvement in onboarding instructions and error messages, which were addressed before final deployment. The system demonstrated stable performance under simulated load, handling up to 100 concurrent rooms without significant latency.

Conclusion
==========

Summary of Aims and Achievements
--------------------------------
The primary aim of this project was to design and implement an online multiplayer game where users guess words based on drawings, with a focus on real-time interaction, security, and scalability. The objectives included building a robust backend with NestJS, a responsive frontend with ReactJS, secure authentication, real-time gameplay using WebSocket, and a scalable deployment using Docker and cloud services. Through careful planning, iterative development, and comprehensive testing, the project successfully delivered a fully functional game that meets these objectives. The system supports up to eight players per room, provides a fair scoring system, and ensures a smooth user experience across devices. Key lessons learned include the importance of clear requirements, the value of automated testing, and the need for regular user feedback to refine usability and features.

Further Work

While the project achieved its main goals, several areas offer opportunities for further development:
- **Enhanced Game Features:** Adding custom word lists, AI bots, new game modes, and richer drawing tools could increase engagement.
- **Mobile App Development:** Creating native mobile applications for iOS and Android would broaden the user base and improve accessibility.
- **Advanced Analytics:** Integrating analytics for player behavior, game statistics, and performance monitoring could inform future improvements.
- **Internationalization:** Supporting multiple languages would make the game accessible to a global audience.
- **Accessibility Improvements:** Further work could focus on making the game more accessible to users with disabilities, such as improved screen reader support and alternative input methods.
- **Security Enhancements:** Ongoing security audits and the addition of features like two-factor authentication would strengthen user protection.
- **Outstanding Issues:** Some minor UI bugs and rare edge cases in real-time synchronization remain and are documented for future resolution.

Critical Evaluation
-------------------
A detached, objective review of the project reveals both strengths and areas for improvement at each stage of the software development process.

**Requirements:**
The requirements were comprehensive in covering the core gameplay, user management, and security needs. However, some non-functional requirements, such as detailed accessibility standards and advanced analytics, were not fully specified at the outset. In retrospect, involving a broader range of stakeholders earlier could have uncovered additional user needs. The requirements were generally not overly prescriptive, allowing for flexibility in design and implementation.

**Design:**
Multiple design alternatives were considered, especially regarding backend frameworks (NestJS vs. Express.js) and frontend libraries (ReactJS vs. Vue.js/Angular). The chosen solutions proved effective for the project's scale and goals. The use of class and ER diagrams, sequence and state diagrams, and wireframes provided a solid foundation. However, more detailed modeling of error states and accessibility features could have improved the design further. The design process was iterative, with regular reviews and updates based on feedback and testing.

**Implementation:**
The implementation closely followed the design, with only minor deviations due to technical constraints or new insights gained during development. The use of TypeScript across the stack improved maintainability and onboarding. Automated CI/CD pipelines and Docker-based deployment streamlined the process. Some challenges, such as optimizing real-time performance and handling concurrent user actions, required additional research and refactoring. The team adapted well, using agile practices to address issues as they arose.

**Testing:**
The layered testing strategy (unit, integration, system, and user testing) was effective in identifying and resolving defects. Automated tests provided high coverage for critical modules, while manual testing uncovered usability issues. Some areas, such as accessibility and performance under extreme load, could benefit from more targeted testing in the future. The inclusion of user feedback in the testing process was particularly valuable for refining the user experience.

**Review of Plan and Deviations:**
The original project plan was generally followed, with most milestones achieved on schedule. Some deviations occurred due to unforeseen technical challenges and the need for additional user testing. These were managed through regular sprint reviews and adjustments to the timeline. The agile approach allowed the team to remain flexible and responsive to change.
